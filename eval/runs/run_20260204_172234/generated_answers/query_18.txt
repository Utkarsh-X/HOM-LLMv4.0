## Component Interactions

1. **Query Planner and Caching**: A `QueryPlanner` instance (which holds the `plan_cache`) is the entry point for processing a query. When a query is submitted, the `QueryPlanner` first checks its `plan_cache` to see if an execution plan for that specific query already exists.
* If a plan is found (cache hit), it's retrieved directly, saving optimization and plan generation time. The `plan_stats` are updated.
* If no plan is found (cache miss), the `QueryPlanner` proceeds to generate one. The `plan_stats` are updated.

2. **Query Planner and Optimizer**: In case of a cache miss, the `QueryPlanner` (or a component it uses) will parse the raw query string into an intermediate representation, `QueryOperations`. It then invokes the `Optimizer`'s `optimize` method, passing these `QueryOperations`.

3. **Optimizer and Rules**: The `Optimizer`'s `optimize` method sequentially applies the five optimization rules:
* `_apply_predicate_pushdown`: Modifies `QueryOperations` to filter data as early as possible.
* `_apply_projection_pushdown`: Modifies `QueryOperations` to select only necessary columns.
* `_apply_constant_folding`: Evaluates constant expressions in filters to simplify them.
* `_apply_index_selection`: Determines if an index can be used based on `QueryFilter`s and `available_indices`.
* `_apply_join_reordering`: Reorders join operations if multiple joins are present, potentially reducing cost.
During this process, the `Optimizer` records its own `optimization_time_ms` in `optimization_stats`. The result is an `OptimizedQuery` object, containing the modified `QueryOperations` and estimated cost.

4. **Query Planner and Plan Generation**: After optimization, the `QueryPlanner` uses the `OptimizedQuery` (specifically, its `optimized` `QueryOperations`) to generate a concrete `QueryPlan`. This involves calling a method like `_generate_plan_steps`, which translates the optimized operations into an ordered list of `PlanStep`s (e.g., `TABLE_SCAN`, `FILTER`, `PROJECT`, `JOIN`, `SORT`, `LIMIT`). The generated `QueryPlan` is then stored in the `plan_cache` for future use (if caching is enabled).

5. **Query Planner and Executor**: Once a `QueryPlan` is available (either from cache or newly generated), the `QueryPlanner` passes it to the `QueryExecutor`'s `execute` method.

6. **Executor and Execution Timing**: The `QueryExecutor` takes the `QueryPlan` and initiates an `ExecutionContext` for it.
* The `ExecutionContext` records the `start_time` of the execution.
* The `QueryExecutor` iterates through each `PlanStep` in the `QueryPlan`, calling `_execute_step` for each.
* For every `_execute_step` call, the `QueryExecutor` records the `step_start` and `step_duration`, adding these details to the `ExecutionContext`'s `execution_stages`.
* Upon completion of all steps (or an error), `context.finish()` is called, setting the `end_time`.
* The total execution duration (`get_duration_ms`) and other metrics (`rows_processed`) are calculated and updated in the `QueryExecutor`'s `execution_stats`.

## Summary

In complex queries, the system orchestrates a multi-stage process involving optimization, caching, and detailed timing. When a query is received, a `QueryPlanner` first checks its `plan_cache`. If a plan exists (cache hit), it's retrieved immediately, bypassing the costly optimization and plan generation phases, thus improving performance. If no plan is cached (cache miss), the `QueryPlanner` initiates the optimization process.

The `Optimizer` then takes the query's operations and sequentially applies five distinct rules: Predicate Pushdown, Projection Pushdown, Constant Folding, Index Selection, and Join Reordering. These rules transform the query into a more efficient form, aiming to reduce the amount of data processed and the overall execution cost. The `Optimizer` meticulously tracks the time spent on this optimization.

Following optimization, the `QueryPlanner` generates a concrete `QueryPlan` consisting of ordered `PlanStep`s (e.g., `TABLE_SCAN`, `FILTER`, `JOIN`). This newly generated plan is then stored in the `plan_cache` for future identical queries.

Finally, the `QueryExecutor` takes this `QueryPlan` and executes each `PlanStep` in sequence. An `ExecutionContext` is created to precisely measure the total execution duration and the duration of each individual step. This detailed timing information, along with metrics like rows processed, is recorded and made available, providing deep insights into the query's runtime performance and identifying potential bottlenecks. This integrated approach ensures that queries are not only executed efficiently but also that their performance characteristics are thoroughly monitored.
