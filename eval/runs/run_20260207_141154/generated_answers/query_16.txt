## Summary

**Partial Failures:**
The `BatchProcessor` handles partial failures at the batch level by isolating the processing of each batch within a `try-except` block. If an exception occurs during the execution of the `processor_func` for a specific batch:
* The exception is caught, preventing the entire processing operation from crashing.
* An error message detailing the failure is appended to the `errors` list within the `BatchResult`.
* The `failed_count` in the `BatchResult` is incremented by the number of items in the failed batch.
* An optional `error_handler` callback can be invoked to allow external components to react to the failure.
* Crucially, the `BatchProcessor` continues to process subsequent batches, ensuring that a failure in one batch does not prevent other batches from being attempted. Only results from successfully processed batches are accumulated.

Based on the provided code, the `BatchProcessor` itself **does not inherently implement at-least-once semantics**.
* Each batch is processed exactly once by the `processor_func`.
* If a batch fails, it is marked as failed, its items contribute to `failed_count`, and an error is recorded. However, the `BatchProcessor` does not contain any internal retry logic to re-process these failed batches or items.
* To achieve at-least-once semantics, the responsibility would fall to the *caller* of the `BatchProcessor.process` method. The `BatchResult` object provides the necessary information (`failed_items`, `errors`) for the caller to identify which items or batches failed and then implement a retry mechanism by re-submitting those specific items for processing.
