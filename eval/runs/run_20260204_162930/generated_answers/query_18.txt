The following components are involved in query optimization, plan caching, and execution timing:

* **Purpose:** Applies a sequence of optimization rules to a query's operations to produce a more efficient execution strategy.
* **Optimization Rules (5 explicitly applied in `optimize` method):**
1. **Predicate Pushdown (Symbol 116):** Moves filters as early as possible in the execution plan, reordering them by estimated selectivity (`_estimate_selectivity`).
2. **Projection Pushdown:** Selects only the columns needed for subsequent operations, reducing data transfer. (Implementation not provided, but applied in `optimize`).
3. **Constant Folding (Symbol 139):** Evaluates constant expressions at compile time, simplifying filters or other operations.
4. **Index Selection:** Chooses the most efficient index for data access. (Implementation not provided, but applied in `optimize`).
5. **Join Reordering:** Changes the order of join operations to minimize intermediate result sizes. (Implementation not provided, but applied in `optimize`).
* **Timing:** Records `optimization_time_ms` for each optimization run.

2. **QueryPlanner (Symbol 92, 102):**

* **Plan Generation:** `_generate_plan_steps` (Symbol 136) creates an initial list of `PlanStep` objects based on query keywords (e.g., "SELECT", "WHERE", "JOIN").

3. **QueryPlan (Symbol 31):**
* **Purpose:** Represents a complete query execution plan, consisting of an ordered list of `PlanStep` objects.
* **Attributes:** `plan_id`, `steps`, `total_cost` (sum of step costs), `total_estimated_rows`.

4. **PlanStep (Symbol 23):**
* **Purpose:** Defines a single operation within a `QueryPlan` (e.g., `TABLE_SCAN`, `FILTER`, `JOIN`, `SORT`, `LIMIT`).
* **Attributes:** `operation`, `parameters`, `estimated_output_rows`, `estimated_cost`.

5. **ExecutionContext (Symbol 16):**
* **Purpose:** Tracks timing and statistics for a single query's execution.
* **Timing:** Records `start_time`, `end_time`, and calculates `get_duration_ms()`.
* **Statistics:** Tracks `rows_processed` and `execution_stages`.

6. **ExecutionEngine (Symbol 57, 151):**
* **Purpose:** Executes the steps of a `QueryPlan`.
* **Timing:** Aggregates `total_duration_ms` and `total_rows_processed` across all executed queries in `execution_stats`.
* **Execution:** `_execute_step` dispatches to specific handlers for each `PlanOperation`.

## Component Interactions

The components interact in a sequence that involves plan generation, optimization, caching, and execution timing:

1. **Query Plan Request:** A query string is submitted, typically to the `QueryPlanner`.
2. **Plan Caching (QueryPlanner):**
* The `QueryPlanner.plan_query` method first generates a `cache_key` for the incoming query.
* It checks `self.plan_cache` for an existing `QueryPlan` associated with this key.
* **Cache Hit:** If found, the cached `QueryPlan` is immediately returned, incrementing `plan_stats["cache_hits"]`. This bypasses plan generation and optimization.
* **Cache Miss:** If not found, `plan_stats["cache_misses"]` is incremented, and a new plan generation process begins.
3. **Initial Plan Generation (QueryPlanner):**
* For a cache miss, `QueryPlanner._generate_plan_steps(query)` is called. This method *mocks* parsing the query string and produces an initial, unoptimized list of `PlanStep` objects.
4. **Optimization (QueryOptimizer):**
* **Assumption:** An external orchestrator (not explicitly shown in the provided code) takes the initial query representation (or the `PlanStep`s from `QueryPlanner` converted into `QueryOperations`) and passes it to the `QueryOptimizer`.
* `QueryOptimizer.optimize` starts a timer (`start_time`) to measure optimization duration.
* It sequentially applies the 5 optimization rules: Predicate Pushdown, Projection Pushdown, Constant Folding, Index Selection, and Join Reordering. Each rule modifies the `QueryOperations` representation to improve efficiency.
* After applying rules, the optimizer estimates the cost of the `optimized` query.
* The `optimization_time_ms` is calculated and stored in the `OptimizedQuery` result.
* **Assumption:** The `OptimizedQuery.optimized` (which is `QueryOperations`) is then converted back into a `List[PlanStep]` to form the final, optimized `QueryPlan`.
5. **Plan Caching (QueryPlanner - continued):**
* The newly generated and *optimized* `QueryPlan` is then stored in `QueryPlanner.plan_cache` if `enable_caching` is true. `plan_stats["plans_generated"]` is incremented.
6. **Execution Timing (ExecutionContext & ExecutionEngine):**
* The (cached or newly optimized) `QueryPlan` is passed to the `ExecutionEngine` for execution.
* An `ExecutionContext` is created for the specific query, recording its `start_time`.
* The `ExecutionEngine` iterates through each `PlanStep` in the `QueryPlan`, calling `_execute_step` for each.
* During execution, the `ExecutionContext` tracks `rows_processed` and `execution_stages`.
* Upon completion, `ExecutionContext.finish()` sets the `end_time`, allowing `get_duration_ms()` to report the total execution time.
* The `ExecutionEngine` aggregates these individual query durations and row counts into its `execution_stats`.

## Execution Trace

The execution flow for a complex query, combining optimizer rules, execution timing, and plan caching, proceeds as follows:

1. **Query Initiation:** A query string is provided to the system, typically initiating a call to a `QueryPlanner` instance.
2. **Plan Cache Lookup (QueryPlanner.plan_query):**
* `QueryPlanner._make_cache_key(query)` is invoked to generate a unique identifier for the query.
* The `QueryPlanner` checks `self.plan_cache` using this `cache_key`.
* **Path A: Cache Hit:** If the `cache_key` is found in `self.plan_cache`:
* `self.plan_stats["cache_hits"]` is incremented.
* The pre-existing `QueryPlan` is retrieved and returned.
* Execution proceeds directly to step 6 (Execution).
* **Path B: Cache Miss:** If the `cache_key` is not found:
* `self.plan_stats["cache_misses"]` is incremented.
* `QueryPlanner._generate_plan_steps(query)` is called (Symbol 136). This method *mocks* parsing the query (e.g., checking for "SELECT", "WHERE", "JOIN") and constructs an initial, unoptimized `List[PlanStep]`.
3. **Query Optimization (QueryOptimizer.optimize):**
* **Assumption:** The initial query representation (derived from the query string or the `PlanStep`s) is passed to a `QueryOptimizer` instance.
* `QueryOptimizer.optimize(operations)` (Symbol 65) is called.
* `import time; start_time = time.time()` records the beginning of optimization.
* The `QueryOptimizer` applies its 5 rules sequentially to the `QueryOperations` object:
* `optimized = self._apply_predicate_pushdown(optimized)` (Symbol 116): Reorders filters.
* `optimized = self._apply_projection_pushdown(optimized)`: Selects necessary columns.
* `optimized = self._apply_constant_folding(optimized)` (Symbol 139): Evaluates constants.
* `index_used = self._apply_index_selection(optimized)`: Selects an index.
* `if optimized.joins: optimized = self._apply_join_reordering(optimized)`: Reorders joins.
* `estimated_cost = self._estimate_cost(optimized)` calculates the cost of the optimized plan.
* `optimization_time = (time.time() - start_time) * 1000` calculates the duration.
* An `OptimizedQuery` object is returned, containing the `optimized` operations, `estimated_cost`, and `optimization_time_ms`.
4. **Final Plan Creation (QueryPlanner):**
* **Assumption:** The `OptimizedQuery.optimized` (which is `QueryOperations`) is converted back into a `List[PlanStep]` to form the final, optimized `QueryPlan`.
* A `QueryPlan` object is instantiated with the `cache_key` and the optimized `List[PlanStep]`.
5. **Plan Cache Storage (QueryPlanner.plan_query):**
* If `self.enable_caching` is true, the newly created and optimized `QueryPlan` is stored in `self.plan_cache[cache_key]`.
* `self.plan_stats["plans_generated"]` is incremented.
* The `QueryPlan` is returned.
6. **Query Execution (ExecutionEngine):**
* The `QueryPlan` (either from cache or newly generated/optimized) is passed to an `ExecutionEngine`.
* An `ExecutionContext` (Symbol 16) is created for the query, recording `self.start_time = time.time()`.
* The `ExecutionEngine` iterates through `QueryPlan.steps`. For each `step`:
* `self._execute_step(step, intermediate_result, context)` (Symbol 151) is called.
* This method dispatches to specific execution functions based on `step.operation` (e.g., `_execute_table_scan`, `_execute_filter`, `_execute_join`).
* `ExecutionContext.rows_processed` is updated.
* Upon completion of all steps, `ExecutionContext.finish()` is called, setting `self.end_time = time.time()`.
* `ExecutionContext.get_duration_ms()` provides the total execution time for this specific query.
* The `ExecutionEngine` updates its `self.execution_stats` (Symbol 57) with `queries_executed`, `total_duration_ms`, and `total_rows_processed`.

## Summary

In complex queries, the system combines optimizer rules, execution timing, and plan caching through a multi-stage process. Initially, a `QueryPlanner` attempts to retrieve a pre-optimized `QueryPlan` from its `plan_cache` using a generated `cache_key`. If a cache hit occurs, the cached plan is used directly, saving time.

Upon a cache miss, the `QueryPlanner` generates an initial set of `PlanStep`s. This initial representation is then (implicitly, as per assumption) passed to a `QueryOptimizer`. The `QueryOptimizer` applies a sequence of 5 rules: Predicate Pushdown, Projection Pushdown, Constant Folding, Index Selection, and Join Reordering. During this phase, the `QueryOptimizer` measures the `optimization_time_ms`. The result is an `OptimizedQuery` which is then converted back into an optimized `QueryPlan`. This newly optimized plan is then stored in the `QueryPlanner`'s cache for future use.

Finally, the (cached or newly optimized) `QueryPlan` is executed by an `ExecutionEngine`. An `ExecutionContext` is created for each query to meticulously track its `start_time`, `end_time`, and `rows_processed`, allowing for precise measurement of `get_duration_ms()`. The `ExecutionEngine` aggregates these individual query execution statistics, providing overall performance metrics. This integrated approach aims to reduce query latency by reusing optimized plans and improving execution efficiency through rule-based transformations, while providing detailed timing information for performance analysis.
