## Component Interactions

The `BatchProcessor` handles partial failures by processing items in discrete batches and isolating failures to individual batches.

1. **Batch Creation and Iteration (lines 50-54):** The `process` method first splits the input `items` into smaller `batches` based on the configured `self.batch_size`. It then iterates through these `batches` sequentially.
2. **Batch Processing and Error Isolation (lines 59-74):** For each `batch`, the `BatchProcessor` invokes the provided `processor_func(batch)` within a `try-except` block.
* **Successful Batch:** If `processor_func` executes without raising an exception, its `batch_results` are `extend`ed to the overall `results` list, and `processed_count` is incremented by the number of items in the successful batch (lines 60-62).
* **Failed Batch:** If `processor_func` raises an `Exception` for a particular batch, the exception is caught (line 65).
* An `error_msg` is created, indicating the failed batch index and the exception string, and appended to the `errors` list (lines 66-67).
* The `failed_count` is incremented by the total number of items in the *failed batch* (line 68).
* If an `error_handler` callable was provided during the `process` method call, it is invoked with the caught `Exception` (lines 70-71).
* The error is logged (line 73).
* Crucially, after handling the exception, the loop continues to the *next* batch (line 57), allowing subsequent batches to be processed even if a preceding one failed.
3. **Result Aggregation (lines 76-85):** After iterating through all batches, the `process` method compiles a `BatchResult` object. This object includes:
* `processed_items`: The count of items from successfully processed batches.
* `failed_items`: The count of items from batches that encountered an exception.
* `errors`: A list of error messages, one for each failed batch.
* `results`: The aggregated results from all successfully processed batches.

This interaction pattern ensures that a failure in one batch does not halt the entire processing operation, thus implementing partial failure handling.

## Summary

**Partial Failure Handling:**
The `BatchProcessor` explicitly handles partial failures at the batch level. If the `processor_func` encounters an exception while processing a specific batch, that failure is isolated to that batch. The `BatchProcessor` records the error, increments a `failed_count` for the items in that batch, and optionally invokes a user-defined `error_handler`. Processing then continues with subsequent batches. The final `BatchResult` clearly distinguishes between `processed_items` and `failed_items`, and provides a list of `errors` for the batches that failed. This allows the caller to understand which parts of the overall operation succeeded and which failed.

**At-Least-Once Semantics:**
Based on the provided code, the `BatchProcessor` itself **does not implement at-least-once semantics** for the `processor_func`. The `process` method iterates through batches, and each batch is submitted to the `processor_func` exactly once. If a batch fails (i.e., `processor_func` raises an exception), the `BatchProcessor` records the failure and moves on to the next batch without automatically retrying the failed batch. To achieve at-least-once semantics, the caller of `BatchProcessor.process` would need to inspect the `BatchResult` (specifically `failed_items` and `errors`) and implement its own retry logic to re-submit the failed items or batches in a subsequent call. The `BatchProcessor` provides the necessary information for a higher-level system to implement such a retry mechanism, but does not perform it internally.
