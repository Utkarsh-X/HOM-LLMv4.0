## Component Interactions

When a request is made to `CacheManager.get(namespace, identifier, fetch_func, ttl)` and all cache layers miss, the following interactions occur, along with cache promotion:

1. **L1 Memory Cache Check (Initial Lookup)**:
* The `get` method first generates a `key` using `_generate_key`.
* It checks if the `key` exists in `self.memory_cache` and if its timestamp (`self.memory_timestamps[key]`) indicates it's still valid within the `ttl`.
* **L1 Miss**: If the key is not found or has expired, the entry is removed (if expired), and `self.stats["memory_misses"]` is incremented (Symbol: 91, File: cache_manager.py, lines 20-24). The system then proceeds to check the L2 Redis cache.

2. **L2 Redis Cache Check**:
* If L1 misses, the `CacheManager` checks if Redis is enabled (`self.redis` is not `None`).
* It attempts to retrieve the value from Redis using `self.redis.get(key)`.
* **L2 Miss**: If `redis_value` is `None` (meaning the value is not in Redis), `self.stats["redis_misses"]` is incremented (Symbol: 91, File: cache_manager.py, lines 32-33). The system then proceeds to fetch from the ultimate source.

3. **L3 Database (Source) Fetch**:
* If both L1 and L2 miss, and a `fetch_func` was provided, this function is executed: `value = fetch_func()` (Symbol: 91, File: cache_manager.py, line 36). This `fetch_func` is responsible for retrieving the data from the original data source, which is conceptually the L3 database (as indicated by the `CacheLayer.DATABASE` enum and external context mentioning "would query database").
* **Cache Promotion (L3 to L2 and L1)**: If `fetch_func` successfully returns a `value`, this value is then promoted to both the L2 Redis cache and the L1 memory cache. This is achieved by calling `self.set(namespace, identifier, value, ttl)` (Symbol: 91, File: cache_manager.py, line 37).
* The (implied) `set` method would first store the `value` in Redis using `self.redis.set(key, value, ex=ttl)`.
* Then, it would call `self._set_memory(key, value, ttl)` to store the `value` in the L1 memory cache. The `_set_memory` method handles potential LRU eviction if `self.memory_cache` has reached its `memory_limit` before adding the new entry (Symbol: 160, File: cache_manager.py, lines 4-11).
* The fetched `value` is then returned to the caller.

4. **No Value Found**: If `fetch_func` is not provided or returns `None`, and all caches have missed, the `get` method returns `None` (Symbol: 91, File: cache_manager.py, line 39).

**Cache Promotion Mechanism**:
Cache promotion occurs in two main scenarios:
* **L2 to L1 Promotion**: If a value is found in the L2 Redis cache after an L1 memory cache miss, `self.stats["redis_hits"]` is incremented, and the value is immediately promoted to the L1 memory cache by calling `self._set_memory(key, redis_value, ttl)` (Symbol: 91, File: cache_manager.py, lines 29-30). This ensures subsequent requests for the same data can be served faster from L1.
* **L3 to L2 and L1 Promotion**: When a value is successfully fetched from the ultimate source (L3 database) after both L1 and L2 misses, it is promoted to both the L2 Redis cache and the L1 memory cache via the `self.set` method. This populates the higher-level caches for future requests.

## Summary

When L1 memory, L2 Redis, and L3 database caches all miss, the `CacheManager.get` method systematically checks each layer. It first attempts to retrieve the data from the L1 in-memory cache. If that misses, it then queries the L2 Redis cache. If both L1 and L2 miss, and a `fetch_func` is provided, this function is executed to retrieve the data from the ultimate source (conceptually the L3 database). Upon successful retrieval from the source, the data is then promoted by being written back to both the L2 Redis cache and the L1 memory cache. This ensures that subsequent requests for the same data can be served from the faster, higher-level caches. Cache promotion also occurs when a value is found in L2 Redis after an L1 memory miss, in which case the value is immediately moved into the L1 memory cache. The `_set_memory` method handles the specifics of L1 promotion, including an LRU eviction policy to manage memory limits.
