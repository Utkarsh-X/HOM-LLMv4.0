## Enumerated Components

The multi-layer cache system described in the context consists of the following components:

1. **CacheManager (Symbol 21):** The central orchestrator for the multi-layer cache. It manages the interactions between different cache layers and the underlying data source.
2. **L1 Memory Cache (Symbol 21, `self.memory_cache`):** An in-process, in-memory dictionary-based cache. It is the fastest layer and has a configurable `memory_limit` (Symbol 40). It uses a Least Recently Used (LRU) eviction policy (Symbol 160).
3. **L2 Redis Cache (Symbol 21, `self.redis`):** An external Redis instance used as a second-layer cache. It is enabled if `redis_enabled` is true during `CacheManager` initialization (Symbol 40). It uses a `RedisClient` (Symbol 42) for interaction.
4. **L3 Database Cache (Conceptual, Symbol 21 docstring, Symbol 15):** Mentioned in the `CacheManager`'s docstring as a layer and in the `CacheLayer` enum. However, the `CacheManager`'s `get` method does not directly manage or interact with a dedicated "database cache" layer. Instead, it relies on a `fetch_func` to retrieve data from the ultimate source, which is implicitly the "database" or primary data store.
5. **`fetch_func` (Callable, Symbol 21 `get` method parameter):** A function provided to the `get` method that is responsible for fetching the actual data from the primary data source (e.g., a database) when all cache layers miss.

## Component Interactions

When a request is made to retrieve a value using the `CacheManager.get` method (Symbol 21), the following sequence of interactions occurs:

1. **L1 Memory Cache Check:**
* The `CacheManager` first generates a cache `key` (Symbol 83).
* It checks if the `key` exists in `self.memory_cache` (L1).
* If found and not expired (based on `self.memory_timestamps` and `ttl`), it's an L1 hit, `self.stats["memory_hits"]` is incremented, and the value is returned immediately.
* If the key is found but expired, it's removed from L1.
* If the key is not found or expired, `self.stats["memory_misses"]` is incremented, and the process proceeds to L2.

2. **L2 Redis Cache Check:**
* If L1 misses and Redis is enabled (`self.redis` is not None), the `CacheManager` attempts to retrieve the value from Redis using `self.redis.get(key)`.
* **Cache Promotion (L2 to L1):** If Redis returns a value (`redis_value is not None`), it's an L2 hit. `self.stats["redis_hits"]` is incremented. The value is then *promoted* to the L1 memory cache by calling `self._set_memory(key, redis_value, ttl)` (Symbol 21). This ensures subsequent requests for the same key will hit L1. The value is then returned.
* If Redis does not return a value (`redis_value is None`), it's an L2 miss. `self.stats["redis_misses"]` is incremented, and the process proceeds to the ultimate data source.

3. **L3 Database / Primary Data Source Fetch (All Caches Miss):**
* If both L1 and L2 caches miss, the `CacheManager` checks if a `fetch_func` was provided to the `get` method.
* If `fetch_func` is available, it is executed (`value = fetch_func()`) to retrieve the data from the primary source (e.g., a database).
* **Cache Promotion (Source to L1 and L2):** Once the `value` is fetched, it is then *promoted* to both L1 and L2 caches by calling `self.set(namespace, identifier, value, ttl)` (Symbol 21). The `set` method (Symbol 139) internally calls `self._set_memory(key, value, ttl)` for L1 and `self.redis.set(key, value, ttl=ttl)` for L2. This populates the higher cache layers for future requests. The fetched value is then returned.
* If `fetch_func` is not provided, and all caches miss, the `get` method returns `None`.

## Summary

When L1 memory, L2 Redis, and the conceptual L3 database caches all miss, the `CacheManager`'s `get` method first checks the L1 memory cache. If a miss occurs (either not found or expired), it then checks the L2 Redis cache. If both L1 and L2 miss, the system relies on a provided `fetch_func` to retrieve the data from the primary data source (which is implicitly the L3 database or ultimate source).

Cache promotion works by moving data from a slower, lower-level source to faster, higher-level caches. Specifically:
1. If data is found in the L2 Redis cache (an L2 hit), it is immediately promoted and stored in the L1 memory cache.
2. If data is retrieved from the primary data source via the `fetch_func` (after both L1 and L2 misses), it is then promoted and stored in both the L1 memory cache and the L2 Redis cache.

This multi-layer approach with automatic promotion ensures that frequently accessed data is moved closer to the application, reducing latency for subsequent requests. The `CacheManager` tracks hits and misses for L1 and L2, but the interaction with the L3 database is abstracted through the `fetch_func`, without explicit L3 hit/miss tracking within the `CacheManager` itself.
