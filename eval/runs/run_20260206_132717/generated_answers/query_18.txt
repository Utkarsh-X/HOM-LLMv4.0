## Enumerated Components

The following components are relevant to how optimizer rules combine with execution timing and plan caching:

1. **QueryPlanner (Symbol: 86):** Manages the generation and caching of query execution plans. It contains a `plan_cache` to store `QueryPlan` objects.
2. **QueryOptimizer (Symbol: 42):** Applies a sequence of 5 specific optimization rules to `QueryOperations`. It also estimates the cost of the optimized query and records the time taken for optimization.
* **Rule 1: Predicate Pushdown (`_apply_predicate_pushdown`):** Reorders filters to apply the most selective ones first.
* **Rule 2: Projection Pushdown (`_apply_projection_pushdown`):** Removes unnecessary columns from projections.
* **Rule 3: Constant Folding (`_apply_constant_folding`):** Evaluates constant expressions in filters.
* **Rule 4: Index Selection (`_apply_index_selection`):** Chooses the best available index for the query.
* **Rule 5: Join Reordering (`_apply_join_reordering`):** Reorders joins based on their estimated cost.
3. **QueryPlan (Implicit):** An object representing the execution plan, containing a list of `PlanStep`s. It is generated by `QueryPlanner` and stored in the cache.
4. **OptimizedQuery (Symbol: 252):** The output of the `QueryOptimizer`, containing the original and optimized `QueryOperations`, estimated cost, index used, and optimization time.
5. **ExecutionContext (Symbol: 16, file: execution_engine.py):** Tracks the actual execution details of a query, including start time, end time, duration, rows processed, and execution stages.
6. **PlanStep (Implicit):** Represents a single operation within a query execution plan (e.g., `TABLE_SCAN`, `FILTER`, `JOIN`, `SORT`, `LIMIT`).
7. **QueryFilter (Symbol: 22):** Represents a filter condition, used by the optimizer rules.
8. **QueryOperations (Implicit):** An object representing the parsed query operations, which is the input to the `QueryOptimizer`.

3. **QueryOptimizer and Query Operations:** The `QueryOptimizer` takes `QueryOperations` as input to its `optimize` method.
* **Assumption:** The `QueryPlan` generated by `QueryPlanner` is either directly convertible to `QueryOperations` or its `PlanStep`s are used to construct `QueryOperations` before being passed to the `QueryOptimizer`.
4. **QueryOptimizer and Optimization Rules:** The `QueryOptimizer` sequentially applies its five rules (`_apply_predicate_pushdown`, `_apply_projection_pushdown`, `_apply_constant_folding`, `_apply_index_selection`, `_apply_join_reordering`) to the `QueryOperations` to transform them into a more efficient form.
5. **QueryOptimizer and Cost Estimation/Timing:** During optimization, the `QueryOptimizer` interacts with its `_estimate_cost` method to calculate the estimated execution cost of the optimized operations. It also records the `optimization_time_ms` using `time.time()`.
6. **OptimizedQuery as Output:** The `optimize` method returns an `OptimizedQuery` object, encapsulating the original and optimized operations, estimated cost, and optimization time.
7. **ExecutionContext and Execution Timing:** An `ExecutionContext` is initialized at the start of a query's actual execution. It records the `start_time` and `end_time` to calculate the `duration_ms` of the query's execution.
* **Assumption:** The `OptimizedQuery`'s `optimized` operations are translated back into `PlanStep`s, which are then executed by an executor (not fully provided in context) that updates the `ExecutionContext` (e.g., `rows_processed`, `execution_stages`).
8. **Execution of Plan Steps:** The `_execute_step` method (part of an assumed executor) processes individual `PlanStep`s, performing operations like `TABLE_SCAN`, `FILTER`, `JOIN`, etc., based on the optimized plan.

## Summary

The system processes complex queries by first attempting to retrieve a `QueryPlan` from a cache managed by the `QueryPlanner`. If a plan is not cached, an initial plan is generated and stored. This plan (represented as `QueryOperations`) is then passed to the `QueryOptimizer`. The `QueryOptimizer` applies a sequence of five rule-based optimizations: Predicate Pushdown, Projection Pushdown, Constant Folding, Index Selection, and Join Reordering. During this process, it estimates the cost of the optimized plan and records the time taken for optimization. The result is an `OptimizedQuery` object. Finally, the optimized plan's steps are executed, with an `ExecutionContext` tracking the actual execution time and other metrics, providing a complete picture from query submission to optimized execution and performance measurement.
