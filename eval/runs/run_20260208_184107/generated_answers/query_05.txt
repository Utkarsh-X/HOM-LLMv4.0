## Enumerated Components
The multi-layer cache system, as described by the `CacheManager` and `CacheLayer` enum, consists of the following layers:
1. **L1 Memory Cache**: Implemented as `self.memory_cache` (a Python dictionary) and `self.memory_timestamps` within the `CacheManager` class. This cache has a configurable `memory_limit` and uses an LRU (Least Recently Used) eviction policy.
2. **L2 Redis Cache**: Implemented using a `self.redis` client (an instance of `RedisClient`) within the `CacheManager` class, which can be enabled or disabled.
3. **L3 Database Cache**: Mentioned in the `CacheManager` docstring and `CacheLayer` enum as the third layer. However, its direct management (e.g., specific database client, read/write logic) is not present within the `CacheManager`'s `get` or `set` methods. Instead, the `CacheManager` relies on an external `fetch_func` to retrieve data from this ultimate source.

## Component Interactions

**Scenario: L1 Memory, L2 Redis, and L3 Database Caches All Miss**

When a request for a value is made via `CacheManager.get(namespace, identifier, fetch_func, ttl)`:

1. **L1 Memory Cache Miss**:
* The `get` method first checks `self.memory_cache` (L1) for the `key` (generated from `namespace` and `identifier`).
* If the `key` is not found, or if it's found but has expired based on `self.memory_timestamps` and the provided `ttl`, it's considered an L1 miss.
* The `self.stats["memory_misses"]` counter is incremented.
* The system then proceeds to check the next layer.

2. **L2 Redis Cache Miss**:
* After an L1 miss, if `self.redis` is enabled, the `get` method attempts to retrieve the value from the Redis cache (L2) using `self.redis.get(key)`.
* If `self.redis.get(key)` returns `None`, it signifies an L2 miss.
* The `self.stats["redis_misses"]` counter is incremented.
* The system then proceeds to the ultimate data source.

3. **L3 Database Cache Miss (and Fetch from Source)**:
* Following both L1 and L2 misses, the `CacheManager` itself does not contain explicit logic to query a "database cache" directly. Instead, it checks if a `fetch_func` was provided to the `get` method.
* **If `fetch_func` is provided**: This function is invoked (`value = fetch_func()`). This `fetch_func` is responsible for retrieving the data from the ultimate source, which is implicitly the "Database cache (L3)" or the primary data store.
* If `fetch_func` successfully returns a `value`, this value is then promoted back up the cache hierarchy.
* **If `fetch_func` is not provided**: The `get` method returns `None`, indicating that the requested value could not be found in any managed cache layer or retrieved from a source.

**Cache Promotion Mechanism**

Cache promotion occurs when data is found in a lower-level cache or fetched from the source, and then stored in higher-level caches to improve future access times:

1. **Promotion from L2 (Redis) to L1 (Memory)**:
* If a value is found in the Redis cache (L2) after an L1 miss (`redis_value is not None`), it is immediately promoted to the memory cache (L1).
* This is achieved by calling `self._set_memory(key, redis_value, ttl)`. The `_set_memory` method stores the `value` in `self.memory_cache` and updates its timestamp in `self.memory_timestamps`. It also handles LRU eviction if the memory cache limit is reached.

2. **Promotion from Source (L3/`fetch_func`) to L1 (Memory) and L2 (Redis)**:
* If the `fetch_func` successfully retrieves a `value` after both L1 and L2 misses, this `value` is then stored in *both* the memory cache (L1) and the Redis cache (L2).
* This is done by calling `self.set(namespace, identifier, value, ttl)`.
* The `set` method first calls `self._set_memory(key, value, ttl)` to store it in L1.
* Then, if Redis is enabled, it calls `self.redis.set(key, value, ttl=ttl)` to store it in L2.

## Summary

When L1 memory and L2 Redis caches both miss, the `CacheManager` attempts to retrieve the data by invoking a provided `fetch_func`. This `fetch_func` is assumed to be the mechanism for accessing the L3 database cache or the ultimate data source. If the `fetch_func` successfully retrieves the data, that data is then promoted upwards: first stored in the L1 memory cache and then in the L2 Redis cache, making it available for faster access on subsequent requests. If no `fetch_func` is provided or it fails to retrieve data, the `CacheManager.get` method returns `None`.

**Assumptions:**
* The `fetch_func` argument in `CacheManager.get` is the mechanism used to retrieve data from the L3 database cache or the ultimate data source when L1 and L2 caches miss. The `CacheManager` itself does not contain explicit database interaction logic.
* `RedisClient()` is a functional Redis client that correctly stores and retrieves data.
* The `ttl` (time-to-live) mechanism correctly manages cache entry expiration in both L1 and L2.
