Complex queries are processed through a pipeline involving plan generation, optional optimization, caching, and timed execution. When a query is submitted, the system first attempts to retrieve a pre-existing `QueryPlan` from a `plan_cache` using a generated `cache_key`. In case of a cache miss, an initial `QueryPlan` is generated by `_generate_plan_steps`, which parses the query string to identify operations like `TABLE_SCAN`, `JOIN`, `FILTER`, `PROJECT`, `SORT`, and `LIMIT`. While the direct integration point is not explicitly shown in the provided context, conceptually, this initial plan or an intermediate `QueryOperations` representation would then be passed to an `optimize` method. The `optimize` method also tracks its own execution time. The resulting optimized `QueryPlan` is then stored in the `plan_cache` for future use.

Finally, the `ExecutionEngine` takes the `QueryPlan` (whether from cache or newly generated/optimized) and executes it. An `ExecutionContext` is created to meticulously track the query's performance, recording the overall `start_time` and `end_time`, and calculating the total `duration_ms`. The `ExecutionEngine` aggregates these timings and statistics, providing a comprehensive view of the query's execution performance and handling any errors that occur during the process.
