## Enumerated Components
* **L1 Memory Cache:** This is the fastest cache layer, implemented within the `CacheManager` class using `self.memory_cache` (a dictionary for storing values) and `self.memory_timestamps` (a dictionary for tracking entry timestamps for TTL and LRU eviction).
* **L2 Redis Cache:** This is an external, persistent cache layer managed by an instance of `RedisClient` (`self.redis`) within the `CacheManager`. It provides a shared cache across processes.
* **L3 Database/Source:** Conceptually, this represents the ultimate source of truth for the data. In the provided code, it is abstracted by the `fetch_func` argument passed to the `CacheManager.get` method. This function is responsible for retrieving data from its original storage (e.g., a database) when it is not found in L1 or L2.

## Component Interactions
The `CacheManager.get` method orchestrates the interactions between these cache layers and the data source:

1. **L1 Memory Cache Lookup:**
* The `get` method first generates a unique `key` for the requested item.
* It checks if the `key` exists in `self.memory_cache`.
* If found, it verifies if the entry is still valid based on its timestamp and the configured `ttl`.
* If valid, it's an L1 hit, `self.stats["memory_hits"]` is incremented, and the value is returned.
* If found but expired, the entry is removed from `self.memory_cache` and `self.memory_timestamps`.
* If not found or expired, it's an L1 miss, and `self.stats["memory_misses"]` is incremented.

2. **L2 Redis Cache Lookup (after L1 miss):**
* If Redis is enabled (`self.redis` is not `None`), the `get` method attempts to retrieve the value from the Redis cache using `self.redis.get(key)`.
* If the value is found in Redis, it's an L2 hit, and `self.stats["redis_hits"]` is incremented.
* **Cache Promotion (L2 to L1):** The retrieved `redis_value` is then immediately written to the L1 memory cache using `self._set_memory(key, redis_value, ttl)`. This promotes the data to the faster L1 layer for subsequent access. The value is then returned.
* If the value is not found in Redis, it's an L2 miss, and `self.stats["redis_misses"]` is incremented.

3. **L3 Database/Source Fetch (after L1 and L2 miss):**
* If both L1 and L2 miss, and a `fetch_func` was provided to the `get` method, this function is called (`value = fetch_func()`) to retrieve the data from its original source (conceptually the L3 database).
* **Cache Promotion (L3 to L1 and L2):** Once the `value` is successfully fetched, it is then written to *both* the L1 memory cache and the L2 Redis cache using the `self.set(namespace, identifier, value, ttl)` method.
* `self.set` first calls `self._set_memory(key, value, ttl)` to store it in L1. If the L1 memory cache has reached its `memory_limit`, an LRU (Least Recently Used) eviction policy is applied to remove the oldest entry before adding the new one.
* Then, `self.set` calls `self.redis.set(key, value, ttl=ttl)` to store it in L2.
* The newly fetched and cached `value` is then returned.

4. **Complete Miss:**
* If L1 and L2 both miss, and no `fetch_func` is provided, or if the `fetch_func` returns `None`, the `CacheManager.get` method returns `None`, indicating that the data could not be retrieved from any cache layer or the source.

## Summary
When a request for data results in a miss across all cache layers (L1 memory, L2 Redis, and the conceptual L3 database/source), the `CacheManager` proceeds sequentially. It first checks L1, then L2. If both miss, it invokes a provided `fetch_func` to retrieve the data from its original source.

Cache promotion is an automatic process designed to move frequently accessed data closer to the application for faster retrieval. If a value is found in the L2 Redis cache (after an L1 miss), it is immediately promoted and stored in the L1 memory cache. If the value must be fetched from the ultimate source (via `fetch_func` after both L1 and L2 misses), it is then promoted and stored in *both* the L1 memory cache and the L2 Redis cache. The L1 memory cache manages its size using an LRU eviction policy. This multi-layered promotion strategy ensures that data, once retrieved, is made available in the faster cache layers for subsequent requests.
