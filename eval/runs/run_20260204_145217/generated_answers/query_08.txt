## Enumerated Components

The following components are involved in the `ConnectionPool`'s behavior when all connections are in use:

1. **`ConnectionPool` class**: A singleton class responsible for managing database connections.
2. **`acquire` method**: The method used by callers to obtain a connection from the pool.
3. **`release` method**: The method used by callers to return a connection to the pool.
4. **`_lock`**: A `threading.Lock` instance used to ensure thread-safe access to the pool's internal state.
5. **`max_connections`**: An integer attribute defining the maximum number of connections the pool can manage.
6. **`_in_use`**: A `set` storing the `id`s of connections currently checked out and in use by callers.
7. **`_connections`**: A `list` storing available (idle) connections ready to be reused.
8. **`PoolExhaustedError`**: A custom exception raised when the pool cannot provide a connection because `max_connections` has been reached.
9. **`ConnectionError`**: An exception raised if a new connection cannot be established.
10. **`timeout`**: An attribute initialized in `__init__` but not observed to be used in the `acquire` method's logic for handling pool exhaustion.

## Component Interactions

When a caller attempts to acquire a connection from the `ConnectionPool` via the `acquire` method, the following interactions occur:

1. **Lock Acquisition**: The `acquire` method first obtains a lock (`self._lock`) to ensure that the pool's internal state (`_in_use`, `_connections`) is accessed and modified in a thread-safe manner.
2. **Pool Exhaustion Check**: Inside the locked section, the `acquire` method immediately checks if the number of currently in-use connections (`len(self._in_use)`) has reached or exceeded the `max_connections` limit.
3. **Exhaustion Behavior**:
* **If `len(self._in_use) >= self.max_connections`**: The pool is considered exhausted. The `acquire` method **does not wait** for a connection to become available. Instead, it immediately raises a `PoolExhaustedError`, indicating to the caller that no connections are currently available.
* **If `len(self._in_use) < self.max_connections`**: The pool is not exhausted. The `acquire` method proceeds to either reuse an existing connection from `self._connections` or create a new one.
* If `self._connections` is not empty, it pops an available connection.
* If `self._connections` is empty, it attempts to create a new `PostgresAdapter` or `SQLiteLegacyAdapter` connection. If this creation fails, it raises a `ConnectionError`.
* Once a connection is obtained (reused or new), its `id` is added to `self._in_use`, and the connection is returned to the caller.
4. **Connection Release**: When a caller finishes using a connection, they are expected to call the `release` method.
* The `release` method also acquires `self._lock`.
* It removes the connection's `id` from `self._in_use`.
* It then checks if `len(self._connections)` is less than `self.max_connections`. If true, the connection is appended back to `self._connections` for reuse.
* If `len(self._connections)` is already equal to `self.max_connections` (meaning the pool has enough idle connections), the released connection is closed (`conn.close()`) instead of being added back to the pool.

## Summary

When all connections in the custom `ConnectionPool` are in use, and a caller attempts to acquire a new connection, the pool **does not implement a waiting or timeout mechanism**. Instead, it immediately raises a `PoolExhaustedError`. Callers are therefore responsible for handling this exception, which might involve implementing their own retry logic, waiting strategy, or error reporting. The `self.timeout` attribute is present but is not utilized in the `acquire` method to manage waiting behavior during pool exhaustion. Connections are made available again when callers explicitly invoke the `release` method.
