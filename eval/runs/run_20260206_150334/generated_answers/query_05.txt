## Enumerated Components

The caching system described in the context involves the following components:

1. **`CacheManager`**: The central orchestrator of the multi-layer caching system. It is responsible for coordinating cache lookups, writes, and promotions across different layers.
2. **Memory Cache (L1)**: An in-process, in-memory cache implemented as a Python dictionary (`self.memory_cache`) within the `CacheManager` instance. It stores values along with their timestamps for TTL management and employs an LRU eviction policy when its `memory_limit` is reached.
3. **Redis Cache (L2)**: An external, distributed cache layer accessed via a `RedisClient` instance. It is enabled or disabled based on the `redis_enabled` configuration of the `CacheManager`.
4. **Database Cache (L3)**: The ultimate source of data, referred to as the "Database cache (L3)" in the `CacheManager`'s description. In the `get` method's implementation, this layer is represented by a `fetch_func` callback, which is responsible for retrieving the data when it's not found in L1 or L2.
5. **`RedisClient`**: A wrapper class that provides an interface for `CacheManager` to interact with the Redis server, handling connection pooling and basic Redis operations like `get` and `set`.

## Component Interactions

When L1 memory, L2 Redis, and L3 database caches all miss, the following sequence of interactions occurs within the `CacheManager.get` method, along with how cache promotion works:

1. **L1 Memory Cache Miss**:
* The `CacheManager.get` method is called with a `namespace`, `identifier`, an optional `fetch_func`, and `ttl`.
* It first generates a `key` using `_generate_key`.
* It checks `self.memory_cache` (L1) for the `key`.
* If the `key` is not found, or if it is found but has expired (checked against `self.memory_timestamps` and `ttl`), it's considered a memory cache miss.
* The `self.stats["memory_misses"]` counter is incremented.

2. **L2 Redis Cache Miss**:
* Following an L1 miss, the `CacheManager` checks if `self.redis` (the `RedisClient` for L2) is enabled.
* If enabled, it attempts to retrieve the value from Redis by calling `self.redis.get(key)`.
* If `self.redis.get(key)` returns `None`, it signifies a Redis cache miss.
* The `self.stats["redis_misses"]` counter is incremented.

3. **L3 Database Cache Fetch (All Caches Miss)**:
* If both L1 and L2 caches miss, the `CacheManager` checks if a `fetch_func` was provided to the `get` method.
* If `fetch_func` is present, it is executed (`value = fetch_func()`). This function is responsible for retrieving the data from the ultimate source, which the `CacheManager` describes as the "Database cache (L3)".
* If `fetch_func` is not provided, and all caches miss, the `get` method returns `None`.

**Cache Promotion Mechanism**:

Cache promotion ensures that data retrieved from lower layers is moved to higher, faster layers for subsequent access.

* **Promotion from L2 (Redis) to L1 (Memory)**:
* If a value (`redis_value`) is successfully retrieved from the L2 Redis cache (after an L1 miss), it is immediately promoted to the L1 memory cache.
* This is done by calling `self._set_memory(key, redis_value, ttl)`.
* The `_set_memory` method stores the `redis_value` in `self.memory_cache` and updates its timestamp in `self.memory_timestamps`. It also handles LRU eviction if the memory cache limit (`self.memory_limit`) is exceeded.
* After promotion, the `redis_value` is returned to the caller.

* **Promotion from L3 (Database/Source) to L1 (Memory) and L2 (Redis)**:
* If a value (`value`) is successfully fetched by the `fetch_func` (after both L1 and L2 misses), it is promoted to *both* the L1 memory cache and the L2 Redis cache.
* This is achieved by calling `self.set(namespace, identifier, value, ttl)`.
* The `set` method internally performs two operations:
1. It calls `self._set_memory(key, value, ttl)` to store the value in the L1 memory cache.
2. If Redis is enabled (`self.redis` is not `None`), it calls `self.redis.set(key, value, ttl=ttl)` to store the value in the L2 Redis cache.
* After promotion to both layers, the fetched `value` is returned to the caller.

## Summary

When a request for data results in a miss across all cache layers (L1 memory, L2 Redis, and L3 database/source), the `CacheManager` follows a hierarchical lookup strategy. It first checks the L1 memory cache, then the L2 Redis cache. If both miss, it resorts to fetching the data from the ultimate source, represented by a `fetch_func` (L3). Upon successful retrieval from a lower layer, the data is automatically promoted to higher, faster cache layers. Specifically, data found in L2 Redis is promoted to L1 memory, and data fetched from the L3 source is promoted to both L1 memory and L2 Redis. This multi-layer approach, combined with automatic promotion, aims to optimize data access performance by keeping frequently accessed data closer to the application.
