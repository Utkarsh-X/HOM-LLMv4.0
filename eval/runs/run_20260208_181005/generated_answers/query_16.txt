## Component Interactions

The `BatchProcessor` class orchestrates the processing of a list of items by dividing them into smaller batches and applying a `processor_func` to each batch. Its primary interactions regarding partial failures are with the provided `processor_func` and an optional `error_handler`.

1. **Batch Creation and Iteration**: The `BatchProcessor` first splits the input `items` into `batches` based on its configured `batch_size`. It then iterates through these batches sequentially.
2. **Processing Function Execution**: For each `batch`, the `BatchProcessor` invokes the `processor_func` (a `Callable[[List[T]], List[U]]`) within a `try...except` block.
* **Success Path**: If `processor_func(batch)` executes successfully, its returned `batch_results` are `extend`ed into the overall `results` list, and `processed_count` is incremented by the number of items in the batch.
* **Failure Path**: If `processor_func(batch)` raises an `Exception`, the `BatchProcessor` catches it.
* An `error_msg` detailing the batch index and the exception is generated.
* This `error_msg` is appended to the `errors` list, which is part of the final `BatchResult`.
* The `failed_count` is incremented by the total number of items in the *failed batch*.
* The exception `e` is logged using `logger.error`.
* If an `error_handler` (an `Optional[Callable[[Exception], None]]`) was provided during the `process` call, it is invoked with the caught `Exception`.
3. **Continuation on Failure**: Crucially, after catching an exception for a batch, the `BatchProcessor` continues its loop to process the *next* batch. This ensures that a failure in one batch does not halt the entire processing of subsequent batches.
4. **Result Aggregation**: Upon completion of all batches (or attempts to process them), the `BatchProcessor` aggregates the `results` from successful batches, the `errors` from failed batches, and the `processed_count` and `failed_count` into a `BatchResult` object, which is then returned to the caller.

## Summary

**Handling Partial Failures:**
The `BatchProcessor` handles partial failures by isolating failures to individual batches and continuing overall processing.
1. **Batch-level Isolation**: Items are processed in batches. If an error occurs during the processing of a specific batch by the `processor_func`, only that batch is marked as failed.
2. **Error Capture and Reporting**: When a batch fails, the `BatchProcessor` catches the `Exception`, records an error message specific to that batch, and adds it to an `errors` list within the `BatchResult`. The items within that failed batch are counted towards `failed_items`.
3. **Optional Custom Error Handling**: An optional `error_handler` can be provided to the `process` method. If present, this handler is invoked with the exception whenever a batch fails, allowing for custom logging, metrics, or other side effects.
4. **Continued Execution**: The `BatchProcessor` is designed to be resilient; a failure in one batch does not stop the processing of subsequent batches. This allows for partial success of the overall job, where some items are processed successfully while others fail.
5. **Detailed Outcome**: The `BatchResult` object returned by the `process` method provides a comprehensive summary, including `total_items`, `processed_items`, `failed_items`, and a list of `errors`, allowing the caller to understand which parts of the operation succeeded and which failed.

**Implementation of At-Least-Once Semantics:**
Based *solely* on the provided context, the `BatchProcessor` **does not inherently implement at-least-once semantics** for items that fail during processing.
1. **Single Attempt per Batch**: The `BatchProcessor` attempts to process each batch exactly once by calling the `processor_func` for that batch.
2. **No Internal Retry Logic**: If the `processor_func` fails for a given batch, the `BatchProcessor` catches the exception, records the failure, and moves on to the next batch. There is no explicit retry mechanism within the `BatchProcessor.process` method itself to re-process failed batches or individual items from a failed batch.
3. **At-Most-Once Successful Processing by BatchProcessor**: From the perspective of successful processing by the `BatchProcessor`'s `processor_func` call, items in a failed batch are processed zero times successfully.
4. **External Responsibility**: To achieve at-least-once semantics, the responsibility would fall either on the `processor_func` itself (to implement its own internal retries for items within a batch) or on the caller of `BatchProcessor.process` (to inspect the `BatchResult` for `failed_items` and `errors` and then re-submit those specific items for processing in a subsequent call).
